Architecture

How this codebase is layered. Consensus and P2P define the coin; local storage and the Qt shell are replaceable without forking the network.

Golden rule Local storage is not network consensus. A node may store chainstate in LevelDB, RocksDB, libmdbx, or anything else, as long as validation math and P2P rules stay correct. Wallet DB choice is also local.

Data models (conceptual)

Chain / UTXO

Blocks land as raw data under the blocks directory. Indexes and UTXO (chainstate) are key-value data behind CDBWrapper (currently LevelDB). Validation updates coins views; reorgs use undo data.

Wallet

CWallet + CWalletDB persist keys, metadata, and wallet transactions. Today that persistence is Berkeley DB (wallet.dat). Migration to SQLite would touch this layer only.

GUI models

Qt uses model classes (ClientModel, WalletModel, transaction tables) so the UI does not call consensus code directly from widgets. Modern UI components wrap the same models with themed chrome.

What you can change without forking

  • Qt layout, themes, debug tools, meme-stream panels
  • Wallet backend (BDB → SQLite) with dual-stack migration
  • Chainstate engine (LevelDB → RocksDB/libmdbx) with reindex path
  • RPC extras, ZMQ consumers, external GPE / GigaWallet bridges

What you must not casually change

  • Script interpreter consensus results
  • Block / tx validity rules, subsidy, difficulty rules
  • P2P message semantics required for network compatibility
  • Address / key formats users depend on for funds
