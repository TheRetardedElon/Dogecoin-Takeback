Security & hardening

How a Dogecoin Core development machine and running node can be compromised — and what we enforce on this project. Written after prior drive-wipe / possible targeting concerns. We cannot prove past compromise from code alone; we can reduce surface and make the next environment harder to abuse.

Assume funds are independent of “was I hacked?” debates If any mainnet wallet lived on a machine that ran experimental builds with open RPC, root processes, or unknown peer exposure: treat that wallet as potentially burned. Move remaining value only from a clean machine + known-good software after you control keys.

What is (and is not) likely

VectorRealistic for Core client work?Notes for this tree
Exposed JSON-RPC Highest practical risk Default binds localhost only if -rpcallowip unset. Dev often widens this.
P2P memory corruption Real, hard Untrusted peers feed parsers. We did not add custom P2P message handlers in recovery work; stick to review + hardening flags.
UI / external feeds If custom panels Meme stream / price panels must never run as trusted HTML/JS inside the process that holds keys.
Supply chain / toolchain Common on Windows Prefer WSL/Docker non-root builds; verify tarball hashes for depends.
Logs / git secrets Easy footgun Never commit wallet.dat, .cookie, live conf with passwords.

Immediate hardening checklist

ActionCommand / configurationPurpose
Isolate RPC interface rpcbind=127.0.0.1
# never rpcallowip=0.0.0.0/0		 Restrict RPC strictly to localhost unless you have a deliberate tunnel.
Enforce RPC cookie auth Remove plaintext rpcpassword=; use cookie / rpcauth Avoid credentials sitting in conf files and shell history.
Run as low-privilege user adduser --system dogecoin (Linux/WSL) Limits blast radius if the process is exploited.
Sanitize debug logs Review custom LogPrintf; avoid logging secrets Private keys / seeds must never hit disk logs.
Containerized development Build inside WSL2 / Docker (non-root) Isolates toolchain from primary host OS.

Defaults in this codebase (verified)

  • RPC bind: If -rpcallowip is not set, HTTP RPC listens only on 127.0.0.1 and ::1 (src/httpserver.cpp). Setting -rpcbind alone without allowip is ignored with a warning (refuses “bind everyone”).
  • Cookie auth: When no rpcpassword is set, cookie auth is the intended path (see doc/getting-started.md / conf comments).
  • Hardening flags: configure.ac enables stack protector, _FORTIFY_SOURCE=2, RELRO/NOW, PIE where the linker supports them.
  • Mainnet ports: P2P 22556, RPC 22555 (see root README). Scanners target these.

How compromise often looks in a “dev + node” setup

  1. Open RPC during POS/GPE experiments — rpcallowip=0.0.0.0/0 + weak/static password + port forward/NAT slip → remote sendtoaddress / dumpwallet.
  2. Running as Administrator/root — any RCE becomes full host ownership; HDD wipe fits “post-compromise cleanup or malware” better than “consensus bug.”
  3. Wallet + experimental binary on same machine — one bad build or one RPC leak is enough; architecture isolation (hot wallet elsewhere) matters more than rebrand perfection.
  4. Not unique to Dogecoin — same pattern hits Bitcoin Core, Litecoin, etc. when RPC is exposed.

What our recovery work did not do

  • Did not change consensus (DigiShield, AuxPoW, script rules).
  • Did not add remote UI webviews for meme stream into the spend path.
  • Did not open RPC by default in code.
  • Did not implement SQLite write path yet (BDB only for loadable wallets).

Incident response checklist (if you suspect prior compromise)

  • On a clean machine: generate new keys / new wallet; never reuse seeds from the suspect host if they may have been logged.
  • Sweep remaining funds only after keys are controlled offline / known-good software.
  • Search old datadirs for dogecoin.conf with rpcallowip, plaintext passwords, debug.log with secrets.
  • Rotate any passwords used on that host; check forwarded router ports 22555/22556.
  • Rebuild only in WSL/Docker as non-root; keep mainnet wallets off the build machine.
  • Enable OS full-disk encryption and separate “dev” vs “funds” machines if possible.

Recommended dogecoin.conf skeleton (dev node, no external RPC)

# Mainnet or regtest — adjust as needed
# server=1 only if you need local RPC

# RPC: localhost only + cookie auth (do not set rpcpassword in plaintext)
rpcbind=127.0.0.1
# do NOT set rpcallowip unless you understand the risk
# rpcuser / rpcpassword: prefer cookie or rpcauth from share/rpcuser/rpcuser.py

# Reduce accidental exposure
# listen=1 is for P2P (needed for a normal node); RPC is separate

# Logging: avoid dumping wallet internals
# debug=0

Going forward on this project

  • Keep GPE / GigaWallet / meme stream outside the process that holds spend keys when possible.
  • Any future ZMQ/RPC bridges for retail: authenticate, localhost or mTLS, never raw public RPC.
  • Document security changes in this page when we add features that touch network surfaces.
