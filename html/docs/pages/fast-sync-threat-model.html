Fast Sync CDN threat model

What a public snapshot CDN adds to the attack surface — verified against the live GPE layout (static sync.doge…, dump node, app box). Not overkill; not panic.

Updated: 2026-08-09 Related: Fast Sync explained Multi-operator mesh Diagrams
Bottom line CDN does not invent a “hack the chain / print DOGE” path if Core Pro keeps fail-closed file SHA-256 + mapAssumeutxo + background prove. It does add hosting, bandwidth, DNS, and who can write the snapshot files risk. Serious line = publish path + client verification — not “obfuscate the CDN.”
Matches the master diagram CDN box = dumb pipe (static files, HTTPS only, no secrets). Operator box = dump + publish. Node box = local verify / fail closed. See master architecture PNG.

A. Integrity / supply chain

AttackHere?Status
Replace .dat with garbage Only with root/SSH on GPE or dump node No public write; no app “publish snapshot” button; publish = rsync/cron pull
Evil latest.json only Same write path if host compromised JSON points at CDN + full sha256 + hash_serialized; client must enforce digests
Bad mapAssumeutxo in a release Client release process Real long-term risk — not nginx; protect GitHub / signing
Social “download wallet from CDN” Process CDN is UTXO artifacts; binaries stay on GitHub + hashes

Integrity risk = who can write the sync tree and gpednode — not random GET users.

B. Availability (DoS)

ItemStatus
Multi‑GB flood / hotlink Real residual — no rate limit / WAF / edge on sync vhost yet
Origin down Fast Sync fails → IBD fallback (OK if client handles it)
Cert expiry LE auto-renew in place (monitor)

Optional later: Cloudflare in front of sync.doge…, or nginx limit_req / conn limits. Fine to skip until traffic hurts.

D. Role mix (app vs CDN)

ClaimReality
Same server = website + CDN origin Yes on GPE app box — static root, not the Node app, but same OS/root
Website XSS → rewrite latest.json Only after shell/root; no CMS publish button for snapshots
DOGE_RPC_* on web tier Yes for POS — localhost tunnel, not public; high impact for money if app box owned; separate from CDN integrity if clients hash-check
Dump node RPC public No — gpednode 127.0.0.1 only

Confused deputy is reduced (static CDN vhost, no RPC on CDN host name) but not perfect isolation (app + CDN origin co-located). Good enough for now; full split is a later ops upgrade.

E. Client-side (Core Pro)

CDN side already: small latest.json, versioned immutable .dat name, size declared.

Client must: size caps, strict JSON, fixed datadir paths, fail-closed SHA-256, map gate, background prove. Nginx cannot replace that.

How scared? (this setup)

ConcernLevel
CDN alone prints DOGE / forces forkLow if fail-closed + map + prove
CDN / DNS DoS or confusionMedium (no rate limit yet)
Dump node or publish SSH stolenHigh for download integrity
Main site app hackedHigh for money/app; CDN rewrite only after host compromise
Fake “Core wallet” malwareSocial — pin GitHub releases + hashes

Checklist — already good

  • Static-only sync vhost (no PHP/Node on that host name)
  • HTTPS + redirect; no directory listing
  • Small latest.json + versioned .dat + full digests
  • Dump node RPC localhost; not public
  • Dump node separate machine from public web app
  • No CMS “publish snapshot” feature
  • Binaries on GitHub; CDN = UTXO artifacts

Checklist — residual / later

  • Rate limit / edge (Cloudflare or nginx limits) when traffic hurts
  • HSTS on sync vhost
  • Bandwidth monitoring / alerts
  • Publish path: root SSH + cron OK for now; dedicated deploy user later
  • Optional: split CDN origin off app box
  • Mesh M2 multi-URL failover (availability)

What not to do right now

  • No full WAF rebuild overnight
  • No emergency CDN move “for paranoia”
  • Multi-CDN mesh only when M2 needs it — same digests, not more trust
  • No freezing Fast Sync features for CDN theater
Keep shipping Noted and real, not bananas. Treat “who can write the snapshot + client fail-closed” as the serious line. Product can move; ops upgrades are incremental.
