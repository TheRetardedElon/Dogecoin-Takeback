Fast Sync explained (plain language)

What happens when you use Settings → Fast Sync from CDN…, what the ~11 GB file is, what you still need P2P for, and what “background verification” actually means. No marketing fog.

Product: P1 ~90% CDN: sync.doge.gopastearth.com Attested height: 6324519 Engineering: AssumeUTXO
One sentence Fast Sync downloads a pre-built UTXO snapshot, checks hashes fail-closed, makes the wallet tip usable near height H, then your node re-proves history over P2P in the background. The cloud is a dumb download pipe — not your ongoing verifier.

Two ways to get a full node

Normal IBD (P2P)Fast Sync
What you download Many blocks from peers, over days One ~11 GB snapshot file over HTTPS, then peers as needed
When wallet tip is usable Late — after most history is applied Sooner — after load/activate at attested height H
How you know UTXOs are honest You built them yourself from genesis File SHA-256 + attested hash_serialized + background prove
Still need the network? Yes, always Yes — for proof, new blocks after H, normal node life

What “the cloud” is (and is not)

Public CDN: https://sync.doge.gopastearth.com/

  • latest.json — small manifest (URL, file SHA-256, height, notes)
  • utxo-….dat — multi‑GB UTXO snapshot artifact

It does: serve static files over HTTPS.

It does not: run your wallet, validate your spends, replace consensus, or stay mounted as live chainstate/. Live data always stays on local disk (NVMe / real block volume). Never put the datadir on Drive/Dropbox/FUSE and expect LevelDB to be safe.

  1. Manifest — download tiny JSON; read artifact URL + expected digests.
  2. Download — stream to datadir/snapshots/ while hashing (WinHTTP on Windows).
  3. File digest — must match manifest SHA-256 or the file is deleted (fail closed).
  4. Load — install UTXO set into snapshot chainstate (local LevelDB).
  5. Activate — if height is in mapAssumeutxo and coins hash matches, tip can jump near H so the wallet is usable.
  6. Background prove — node still fetches/applies historical blocks over P2P and re-checks hash_serialized. Mismatch → fail closed.

Two hashes (do not mix them up)

HashCoversWhen checked
File SHA-256 Bytes of the CDN .dat file During / after download
hash_serialized Canonical hash of the UTXO set at height H At activate + after background prove

Both must pass. Neither is “the cloud signed your coins forever.”

“So I don’t finish P2P?”

Partly true You skip waiting for classic full IBD before the wallet tip is near current height. You do not leave the network.

You still use P2P for:

  • Headers / historical blocks to prove the snapshot (background)
  • New blocks after H (chain keeps moving)
  • Peers, mempool, normal full-node duties

Trust model (honest)

  • CDN can host a bad file → caught by file SHA-256 if the manifest is correct.
  • Wrong UTXO set → caught by mapAssumeutxo / hash_serialized (this build attests 6324519).
  • Final safety = background prove + normal consensus afterward.
  • There is no “zero risk.” There is detect, refuse, recover.

When to use it (and when not to)

SituationRecommendation
New install / empty datadir Good — Intro Fast path + dialog, or Settings menu
Second datadir for testing Good
Already mid-IBD on same datadir (~50–80%) Avoid — fights disk/CPU/network; messy mix
Want full archival history forever Use Full archive path; don’t prune; optional skip Fast Sync

How to run it in the client

  1. Install dogecoin-1.14.102-win64-setup.exe (or zip) from release/.
  2. Settings → Fast Sync from CDN…
  3. Click Download & activate snapshot (progress + Abort available).
  4. Or on first-run Intro: choose Fast path — dialog may auto-offer when height ≤ 1000.

Console equivalents (advanced):

listassumeutxo
help fetchassumeutxomanifest
fetchassumeutxomanifest "https://sync.doge.gopastearth.com/latest.json"

Full manifest fetch pulls the multi‑GB file. Prefer the GUI dialog on a clean datadir.

Multi-operator mesh (why more hosts help)

One CDN is a good start; many independent operators hosting the same hash-checked artifact make downloads faster (geo, bandwidth) and harder to take offline. That is not “trust more clouds” — clients still require matching digests and background prove.

Full design: Multi-operator mesh (roles, daisy-chain mirrors, maturity M0–M4, operator checklist). CDN security: Fast Sync threat model (what’s real on GPE today vs overkill).
