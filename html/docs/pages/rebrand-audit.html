Bitcoin → Dogecoin rebrand audit

Manual, tiered plan to finish conversion. Not every “bitcoin” string is a bug — some are history, protocol references, or external URLs. We classify before we rewrite.

Do not bulk-replace blindly A global sed of “bitcoin” → “dogecoin” will break copyrights, historical links, some test vectors, and potentially protocol documentation. Use tiers and review.

What is already done (strong)

  • Primary source filenames: dogecoind, dogecoin-cli, dogecoin-tx, dogecoin-qt entry
  • Qt core types: DogecoinGUI, DogecoinApplication, DogecoinUnits, amount/address classes
  • Config template: dogecoin-config.h.in (no bitcoin-config.h.in)
  • Consensus lib header: dogecoinconsensus.h
  • Test harness header: test_dogecoin.h
  • Locales/qrc largely dogecoin-prefixed
  • No broken #include "…bitcoin…" remaining in scanned src
  • T1 (2026-07-28): DOGECOIN_CONF_FILENAME, HMM_DOGECOIND/QT, DOGECOIN_IPC_*
  • T1: BUILD_DOGECOIN_INTERNAL / consensus API usage in benches
  • T1: i18n context dogecoin-core in C++ and all 64 .ts files
  • T1: user-facing “bitcoins” → “dogecoins” in wallet RPC + dialogs

Tier definitions

T0 — Intentionally leave

  • Copyright headers naming Bitcoin Core developers
  • External URLs (bitcointalk, bitcoin.org developer refs) when historically accurate
  • Comments explaining Bitcoin heritage where educational

T1 — Must finish for “proper Dogecoin convention”

Incomplete renames that still say Bitcoin in identifiers, tests, IPC names, or user-visible copy:

T2 — Comments & developer docs

Protocol comments that say “Bitcoin protocol message types” can become “Dogecoin P2P message types (Bitcoin-derived)” for accuracy. Update when editing those files; no need for a risky mega-PR alone.

T3 — Mechanical header guards & include guards

Almost every header still uses #ifndef BITCOIN_FOO_H. Safe mechanical migration to DOGECOIN_FOO_H after a green build, with automated check that no double-include breakage occurs. Prefer one PR: guards only, no logic changes.

Recommended conversion order

  1. Establish Git + green build (so renames are reversible).
  2. T1 functional identifiers (macros, consensus API, resource init, tests).
  3. T1 user-visible strings and RPC help.
  4. i18n context migration (bitcoin-core → dogecoin-core) as its own careful step.
  5. T3 header guards in a mechanical pass.
  6. T2 comments opportunistically; refresh doc/ last.

Definition of “conversion complete”

  • No user-facing “Bitcoin” in Qt UI or RPC help (except intentional history)
  • No public C++ API still named Bitcoin* / bitcoinconsensus* inconsistently
  • All app/resources/tests use dogecoin product names
  • Header guards consistently DOGECOIN_* (optional but desired)
  • Scan script clean under agreed allowlist (copyrights, URLs)
  • Document allowlist in this page

Allowlist (initial)

# Keep / do not auto-rewrite
"The Bitcoin Core developers"   # copyright history
bitcointalk.org                  # historical reference URLs
bitcoin.org/en/developer-reference  # protocol heritage links (update when we host our own)
Bitcoin Core in comparative docs    # when explicitly comparing projects
