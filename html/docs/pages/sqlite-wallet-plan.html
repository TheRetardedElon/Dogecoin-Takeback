SQLite wallet dual-stack plan

Safe path off Berkeley DB for wallets without breaking existing wallet.dat funds. Consensus is untouched.

Started: 2026-07-28 Default backend today: BDB
Current code status Production wallets still use Berkeley DB exclusively. Format detection is landed: we log format, expose it on getwalletinfo, and refuse SQLite files until a real backend exists.

Why dual-stack (not big-bang delete)

  • Users’ money lives in BDB wallet.dat files.
  • BDB versions differ across platforms; compile pain is real.
  • Bitcoin Core proved: SQLite for new wallets + keep BDB for legacy + migrate tooling.
  • Dogecoin is 1.14-class — we cannot drop in modern Bitcoin wallet code wholesale.

Implementation phases

Phase A — Detection (done)

  • Magic-byte probe (SQLite header vs other)
  • Log format at verify
  • getwalletinfo.format field
  • Hard error if SQLite file presented to this build

Phase B — Abstract storage interface (in progress)

  • walletdb_backend.* preference resolve (-walletformat)
  • Unit tests for format detect + resolve rules
  • Contract documented for future Berkeley/SQLite backends
  • Implement Berkeley backend wrapping current CDB behind interface
  • Keep CWalletDB API surface stable for wallet.cpp callers

Phase C — SQLite backend (new wallets only)

  • configure/depends: optional libsqlite3
  • Schema for keys, txs, metadata (map existing BDB key types)
  • Create new wallets as SQLite when -walletformat=sqlite (or default later)
  • BDB remains default until migrate proven

Phase D — migratewallet

  • Read-only BDB dump of keys + txs + metadata
  • Write new SQLite wallet; archive old file
  • RPC/CLI tool; extensive test wallets
  • Never delete old wallet until user confirms + backup check

Phase E — Deprecate BDB

  • Read-only BDB years after majority migration
  • Eventually remove BDB compile dependency

Safety rules

Funds first No automatic overwrite of wallet.dat. Migration always produces a new file and leaves the original unless the user opts in after verification.
  • Local storage only — no consensus / P2P change.
  • Old and new nodes interop on the network regardless of wallet backend.
  • Test on regtest disposable wallets before mainnet paths.
