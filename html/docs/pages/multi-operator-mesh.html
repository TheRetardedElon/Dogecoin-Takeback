Multi-operator mesh

How many independent orgs can host Fast Sync snapshots (and later cold block objects) so bootstrap is faster, closer, and harder to knock offline — without turning “the cloud” into consensus.

Status: M1 live · M2 next Today: GPE CDN Related: Fast Sync explained Diagrams: architecture art Plan: doc/tiered-storage-and-fast-sync.md
One sentence Operators run full nodes + publish hash-checked static files; clients pick any mirror that matches the same digests and attestations. More operators = more bandwidth and geography, not a second ledger.
Where this sits on the master map Mesh is the External — future mirrors strip under the Fast Sync / AssumeUTXO architecture. CDN stays a dumb pipe; clients still fail-closed. First live operator stack: GPENode (dump node + GPE CDN). Diagrams · Master PNG

How the mesh system works (end-to-end)

Think of three layers that must stay separate. Confusing them is how people invent “cloud consensus” by accident.

LayerJobWhoFailure mode if wrong
1. Attestation Declare “height H has UTXO set hash X” Compiled mapAssumeutxo in Core Pro releases (governance / multi-party dumps) Bad map entry = clients can activate a bad set until prove fails — treat as release-critical
2. Delivery mesh Move multi‑GB bytes close to users Dump nodes + CDN mirrors (GPENode first; others later) Outage or slow download — not silent wrong balances if digests enforced
3. Client verify Stream-hash file, load, activate, background prove Every Core Pro node Mismatch → fail closed; user falls back to IBD / re-fetch

Data plane (what moves):

  1. Operator A’s dump node reaches tip (or chosen H) and runs dumptxoutset.
  2. Operator writes latest.json with file SHA-256, height, hash_serialized, and one or more HTTPS URLs.
  3. CDN/mirrors host immutable objects. Daisy-chain: Operator B may rsync A’s artifact only if digests match, or re-dump independently at the same H.
  4. Client resolves manifest → builds candidate URL list → downloads with stream-hash → first success with expected sha256 wins.
  5. Client activates only if map/policy allows; then proves genesis→H over P2P while the tip stays usable.

Control plane (what does not move to the CDN):

  • No “vote” of CDNs on validity.
  • No live chainstate on the wire.
  • No requirement that every operator run GPE merchant software — dump+CDN is enough for Fast Sync.
Speed vs trust Mesh optimizes time-to-bytes (geo, capacity, failover). Trust stays time-to-proof on the client (hashes + background ConnectBlock).

Why this exists

A single CDN (even a good one) has limits: one region’s latency, one org’s bandwidth bill, one outage window. Fast Sync already makes bootstrap possible without a week of pure IBD. The mesh makes it resilient and faster for more people:

  • Closer bytes — pick a mirror near the user (lower RTT, better throughput)
  • Parallel capacity — many pipes serve the same ~11 GB object
  • No single choke point — one host down → try the next URL
  • Open participation — any serious org can dump + host; GPE is first, not exclusive

Speed comes from object delivery (HTTPS mirrors + optional multi-source), not from relaxing verification. Verification stays local and fail-closed.

Three roles (keep them separate)

RoleWhat they runWhat they publishWhat they must not do
Settlement / dump node Full (or pruned-with-care) Dogecoin node at tip; Core Pro with dumptxoutset hash_serialized, height, bestblock; snapshot .dat Serve live LevelDB over the internet; claim “trust me without hashes”
CDN / mirror host Static HTTPS (nginx, R2, S3, …) latest.json + multi‑GB .dat (and later optional blk objects) Act as consensus; run wallet RPC for the public; FUSE-mount as datadir
Client (wallet node) dogecoin-qt / dogecoind Nothing required Activate on digest mismatch; skip background prove for real funds blindly

One org can wear dump + CDN hats (GPE today). Mesh maturity is when dumpers ≠ only one CDN and clients have a list of mirrors.

Trust model (same as single CDN — scaled out)

More operators ≠ more trust by default You do not “trust operator B because they’re big.” You trust matching digests and your local prove.
  1. File SHA-256 — every mirror must serve bytes that hash to the manifest digest.
  2. hash_serialized / mapAssumeutxo[H] — UTXO set must match the attestation in the client binary (or a documented community process for new heights).
  3. Background prove — client still walks history over P2P and re-checks.
  4. Fail closed — wrong file or wrong coins → refuse activate / abort path.

A malicious mirror can only waste your bandwidth or serve a wrong file that fails hash check. A malicious dumper who publishes a bad hash_serialized only hurts people who ship that value without review — the map entry is a release/governance decision, not “whatever the CDN says today.”

“Daisy-chain” means: operator B can pull A’s verified artifact (or re-dump independently at the same H) and host it. Clients do not need a private relationship with every host — only a list of HTTPS URLs and one expected digest.

Manifest shape (target multi-URL)

Today (GPE, single primary URL) works as:

{
  "network": "main",
  "url": "https://sync.doge.gopastearth.com/utxo-….dat",
  "sha256": "…",
  "blocks": 6324519,
  "hash_serialized": "…",
  "bytes": 11498129241
}

Mesh-ready extension (product direction):

{
  "network": "main",
  "sha256": "…",
  "blocks": 6324519,
  "hash_serialized": "…",
  "bytes": 11498129241,
  "urls": [
    "https://sync.doge.gopastearth.com/utxo-….dat",
    "https://mirror.example.org/dogecoin/utxo-….dat",
    "https://cdn2.example.net/utxo-….dat"
  ],
  "mirrors": [
    { "url": "https://…", "region": "eu-west", "operator": "ExampleOrg" }
  ]
}

Client policy (target): try URLs in order (or by latency probe); first successful stream-hash wins; never accept a different sha256 from a “faster” host.

What an operator must do (checklist)

  1. Run a honest full node; reach a stable tip; prefer not mid-corrupt migrate.
  2. dumptxoutset → record hash_serialized, height, bestblock, file SHA-256, size.
  3. Host .dat + latest.json over HTTPS with correct Content-Length / stable URLs.
  4. Publish operator notes (region, contact, retention policy). No secrets in public docs.
  5. Optional: pull another operator’s artifact and re-host only if digests match (daisy-chain mirror).
  6. For new heights: propose mapAssumeutxo entry via the project’s release process — do not expect clients to soft-trust unsigned JSON alone for activation.

What clients will do (target behavior)

  1. Resolve manifest (default GPE URL, or Options custom, or future operator directory).
  2. Build candidate URL list (url + urls[]).
  3. Download with stream-hash; on failure/timeout, next URL; same expected sha256 always.
  4. Load + activate only if attestation / policy allows.
  5. Background prove; keep pruning policy (P2) so disk stays bounded.

Today’s client already does the single-URL path well. Mesh work is mainly manifest multi-URL + client failover and operator runbooks — not a new consensus subsystem.

Relation to IBD / P2P speed

  • Fast Sync (P1) removes most “download every block before tip is usable.”
  • Mesh (this page) makes that snapshot download faster/more available.
  • IBD P0–P0.3 still matters for: people who skip Fast Sync, background prove, tip catch-up, archival nodes.
  • P3 blk CDN later helps prove/reindex when peers suck — still hash-checked objects.

Non-goals

  • No “operator-signed consensus” replacing PoW.
  • No mandatory GPE account for Fast Sync.
  • No live remote chainstate (S3-as-LevelDB).
  • No requirement that every operator run merchant/GPE stack — dump+CDN is enough.
